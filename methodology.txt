1. OVERALL STRUCTURE  [CODE + CONVERSATION]
--------------------------------------------------------------------------------
Single-file HTML/CSS/JS Progressive Web App, no build step, no framework, no
backend. Static files, deployed via GitHub Pages.
Repo: 886ppak/liebherr (repo name is a legacy artifact from before the
rebrand to "Myslewer" — see section 7).

  index.html              - entire app: HTML + <style> + <script>, 4 tabs
  manifest.json            - PWA install manifest

2. TAB 1 - ROPE RETENTIONING  [CONVERSATION]
--------------------------------------------------------------------------------
Purpose: how many parts of line (reeving) are needed to strip enough rope
off the drum for retentioning work, plus the resulting tensioning test
weight.

DO NOT "FIX" THIS FORMULA:
  reeving = Math.ceil((rope - totalLength) / totalLength)
This was explicitly confirmed by the person, more than once, as intentional
- it is NOT a lifting-capacity reeving calculation, even though it looks
like one at a glance and an AI reviewing it cold is likely to assume it's a
bug. It calculates minimum parts of line to spool sufficient rope off the
drum. Leave it exactly as-is unless the person explicitly asks to change
what the calculation is FOR, not just how it looks.

Data: FLEET_BLOCK_SPEC, one entry per crane/boom-config (1650-t3 and
1650-t5 are separate top-level keys - different drum lengths). Each has
w1/p1, w2/p2 (winch drum length/pull), boom length, and blocks[] - each
block has real OEM ballast plate COMBINATIONS (aux[]), not generic weight
increments. This was a deliberate correction after the person's actual
ballast data showed generic "types" didn't match real available plate
combos. r-hook / r-checkweight fields are READONLY, driven only by
dropdown selection - specifically to stop someone entering a ballast number
that doesn't correspond to a real physical plate combination.

3. TAB 2 - MINIMUM HOOK BLOCK WEIGHTS  [CONVERSATION]
--------------------------------------------------------------------------------
Formula: G_kg = L x M x n x F
  L = boom length, M = rope weight/m (by diameter), n = reeving/falls,
  F = empirical reeving-factor table indexed by n.

UNRESOLVED, FLAGGED NOT FIXED: n appears both as a direct multiplier and
inside F (which itself scales with n) - looks like possible double-counting
of the same effect. Raised with the person once; not confirmed wrong, so
left unchanged. Don't silently "correct" this in a future pass - ask again
first, or at minimum re-flag before changing behavior.

Out-of-range rope diameter or reeving count leads to an explicit warning
banner, not a silent fallback. An earlier version silently fell back to a
default value, which was identified as actively dangerous for a tool used
to pick ballast in the field.

minPlateIncrement per crane was corrected from generic assumed values to
each crane's actual confirmed OEM increment (1650: 375kg, 1300: 500kg,
1110: 200kg, etc.), cross-checked against Tab 1's aux[] data for
consistency.

4. TAB 3 - OUTRIGGER SUPPORT POSITIONING ("CAD tab")  [CONVERSATION]
--------------------------------------------------------------------------------
The most conceptually involved tab - nearly every sign convention here was
arrived at through iteration and explicit correction, not derived cleanly
from first principles. Read this fully before touching the math.

4.1 Coordinate system
  Origin = crane's slew center (turret rotation axis), NOT chassis center.
  Front = boom end = top of OEM diagram = internally NEGATIVE Y.
  Rear = cab/counterweight end = bottom of OEM diagram = internally POSITIVE Y.
  baseX = r*sin(angle), baseY = r*cos(angle).
  User "+FWD" input must DECREASE internal Y: shiftY = -shiftYinput.
  This inversion was a specific confirmed correction - removing it silently
  reverses forward/back on the canvas.

4.2 Outrigger labeling (do not renumber)
  P1 = Rear Right, P2 = Front Right, P3 = Front Left, P4 = Rear Left.
  Slew direction symbol: positive angle points "<", negative angle points
  ">" - this was initially backwards and had to be corrected once already.

4.3 Which pads MUST move
  Only the LATERAL component of a shift determines which pads are in the
  crane's actual path of travel:
    shiftX > 0 (right) -> P1, P2 must move
    shiftX < 0 (left)  -> P3, P4 must move
    shiftX === 0 (pure fwd/bwd) -> nothing is required to move
  Confirmed rationale: pads sit laterally offset from the crane's own
  footprint, so a pure fwd/bwd walk never runs the crane over a pad - even
  on a diagonal shift, the lateral component alone governs.

4.4 Three reference frames per leg, shown in the results table
  a) "If Moved" - from CURRENT position: newX = baseX+shiftX, newY = baseY+shiftY
  b) "If Left in Place" - from NEW crane center: relX = baseX-shiftX, relY = baseY-shiftY
  c) "Baseline" - standard OEM target offset, unaffected by any shift.
  Plus a MUST MOVE / optional tag (per 4.3).

4.5 Chassis footprint collision check
  Flags when a pad's "If Moved" target is currently under the crane's own
  chassis - physically impossible to pre-place a mat there before the crane
  actually moves.
  FOOTPRINTS{} = {width, front, rear} per crane, measured from slew center;
  boom overhang deliberately excluded (boom is airborne mid-walk, doesn't
  interfere with ground mats - confirmed, not assumed).
  Collision test: |x| <= width/2 AND -front <= y <= rear.
  Width: pulled from each OEM sheet's "B" dimension (525/80 R25 tire row,
  the fleet's confirmed standard tire). LRT 1100's sheet uses a different
  layout than the LTM sheets - its width (3300mm) had to be confirmed
  directly by the person against the raw drawing, not assumed from the
  dimension that looked most likely at a glance.
  Front/rear (slew-center-relative, not chassis-center) had no single
  printed dimension anywhere - every crane's split was derived via two
  independently cross-validated methods:
    METHOD A ("top-line"): total boom-tip-to-rear-tip dimension at the top
      of the drawing, minus the printed tail segment, minus the front
      overhang segment (boom-tip to front-of-cab) - remainder is
      slew-center-to-front-of-cab.
    METHOD B ("bottom-chain"): sum the individual axle-spacing segments
      along the bottom of the drawing, front-to-back, stopping at the
      point nearest slew center - which sometimes lands PARTWAY through a
      printed segment, not on a clean boundary (e.g. 1300 required
      subtracting exactly 320mm from partway through one segment; 1650
      needed only 1550mm out of a printed 2450mm segment). This partial-
      segment behavior is real, confirmed by the person, not a rounding
      artifact - don't assume a full segment boundary marks the slew
      center without checking.
  Every crane's final front/rear numbers were confirmed by the person
  running at least one method themselves and comparing against the
  independent P1/P4 cross-check (4.6) before being accepted.

4.6 Cross-validation technique (useful for adding cranes later)
  Each leg's stored r/angle already encodes its own slew-center distance via
  r*cos(angle) - compare that against a hand-measured front/rear split as a
  sanity check. A >1-2% disagreement means one of them is wrong. This
  caught a ~220mm error in an early auto-derived guess for the 1160.

4.7 Canvas rendering
  Footprint rectangle centered on the CURRENT (unshifted) origin.
  Every optional (non-MUST-MOVE) leg gets a second "ghost" dot at its "If
  Moved" position, connected by a thin line, red-ringed if it collides with
  the footprint. Added specifically because on a pure fwd/bwd shift EVERY
  leg is optional (4.3) - without the ghost dot nothing visibly changes on
  the canvas even though the numbers underneath do, which confused the
  person before this was added.

5. TAB 4 - REEVING PLAN  [CODE - see coverage note at top]
--------------------------------------------------------------------------------
Everything in this section is reconstructed from reading the actual
implementation. No conversation record of its design decisions was found.

5.1 What it does
  Lets someone pick a crane + boom/head configuration, then a reeving
  way-count (or a named special/auxiliary config), and see: the OEM sheave-
  routing notation as text, a hook-block-type badge, and a diagram.

5.2 Data shape - reeving/manifest.json
  Maps config keys (e.g. "1650-t3", "1250-sks") to one of two shapes:
    a) {normal: [...], american: [...]} - toggle style, for configs with a
       simple numbered progression (most telescopic booms). Each entry:
       {way, hook, lines}. SVG filename for these is NOT stored per-entry -
       it's constructed at render time as way_${way}.svg (seen directly in
       the activeReeveData() function).
    b) {configs: [...]} - flat style, for configs mixing special/auxiliary-
       device/two-hook variants that don't fit a numbered toggle. Each
       entry: {id, label, hook, lines, svg} - svg IS stored explicitly here,
       sometimes null where no artwork is linked.
  isToggleStyle(cfg) picks which shape a given config uses by checking
  whether cfg.normal or cfg.american exists.

5.3 Diagram artwork provenance [CODE - verified by direct inspection]
  All 182 SVGs share the identical transform matrix
  "matrix(0.999726, 0, 0, -0.999726, 0, 2389.082419)" (LRT 1100 files use a
  proportionally scaled variant), each cropped to a different viewBox
  region of the same underlying coordinate space. This is strong physical
  evidence for a single batch PDF-to-SVG vector extraction from one source
  document, matching the in-app disclaimer's own claim: "Diagrams are the
  actual OEM reeving plan artwork (doc. 98036716), extracted directly - not
  redrawn." Not hand-traced; not independently generated per crane.

5.4 UI fix made in this thread (not part of original build)
  Dropdown option text was edited to include the crane model name in every
  <option> itself, not just the parent <optgroup> label - a collapsed
  <select> only ever displays the selected OPTION's own text, so the
  original version showed just "T3 Telescopic Boom" with no crane name
  visible unless the dropdown was reopened. Read as ambiguous.

5.5 Offline bulk-download feature (added in this thread)
  A button that walks the ENTIRE manifest - every crane/config/way, not
  just the currently-selected one - dedupes every referenced SVG filename
  via allReeveSvgFilenames(), and fetches them with limited concurrency (6
  at a time) so every diagram becomes available offline in one action
  instead of only caching on-demand as each is viewed. Relies entirely on
  the existing service-worker fetch-caching behavior (6) - the button
  itself has no direct Cache API access, it just triggers the GETs.

5.6 KNOWN DATA GAP [CODE - verified]
  21 SVG files exist on disk (mostly lrt1100_tele_* and ltm1110_sks_*)
  that are not referenced by ANY manifest entry - confirmed by diffing the
  full set of manifest-referenced filenames against the actual svg/
  directory listing. Whether these are meant to replace currently-linked
  files, fill in existing null svg fields, or are simply unused leftover
  exports is NOT determinable from the code alone. Don't silently link them
  in without asking the person first.

6. SERVICE WORKER / OFFLINE CACHING  [CONVERSATION + CODE]
--------------------------------------------------------------------------------
Two deliberately separate caches:
  APP_SHELL_CACHE (versioned, e.g. 'app-shell-myslewer-v4') - precaches
    index.html, manifest.json, icons. Bump CACHE_VERSION on any change to
    those files. Old app-shell-* caches deleted on activate.
  CONTENT_CACHE (fixed name 'app-content-v1', never versioned or auto-
    cleared) - holds on-demand fetched content, primarily reeving diagrams.
    Deliberately separate so a crew member who's already viewed certain
    diagrams offline doesn't lose access just because an unrelated app
    update bumped CACHE_VERSION. If this cache ever needs a genuine reset,
    change its name once - don't fold it into the versioned cleanup logic.
Fetch handler: cache-first, network fallback, cached-index.html fallback
for failed navigation (so reloads/deep-links work offline).

9. HOW TO RE-EXTRACT REEVING DIAGRAMS FROM AN OEM SOURCE PDF  [CONVERSATION]
--------------------------------------------------------------------------------
Use this whenever a reeving diagram is missing, incomplete, or genuinely
wrong for some crane/config, and the person can supply the source
"EINSCHERPLAN" PDF for it. First done for LTR 1220 (all 15 diagrams: ways
1-14 + 16), which turned out to have TWO separate bugs worth telling apart
before jumping to this procedure:

  a) DISPLAY bug (fixed once, fixed everywhere, no re-extraction needed):
     inline <svg> elements with only a viewBox (no width/height attrs)
     don't reliably compute proportional height via CSS height:auto, and
     once .snippet-wrap got overflow:hidden (for pinch-zoom), that
     ambiguity started silently cropping the BOTTOM of every diagram.
     Fixed globally in fixInjectedSvgSizing() (section 4.7-adjacent JS) by
     explicitly setting aspect-ratio from the SVG's own viewBox at
     injection time. If a diagram looks cut off at the bottom, check this
     is actually still working before assuming the source data is bad.
  b) DATA gap (needs this section's procedure): the SVG file itself is
     genuinely missing content — verified by rendering the raw file's
     path data independently (see 9.1) rather than trusting the app's own
     display. LTR 1220's diagrams were missing the hook symbol + caption
     text entirely; the original extraction (whoever/whatever did it,
     see section 5) simply hadn't captured that part of each diagram.

9.1 Diagnose before re-extracting — confirm it's actually a data gap
  No SVG rendering tool is available in this sandbox by default
  (rsvg-convert, inkscape, cairosvg all absent; ImageMagick's convert
  delegates to rsvg-convert, which is also absent). matplotlib IS
  available and can render the path data manually:
    - Parse the SVG's viewBox and every <path d="..." transform="matrix(...)">.
    - For each path, tokenize the d-string (this fleet's diagrams only
      ever use M/L commands — straight segments, no curves — so a simple
      "M x y L x y L x y..." tokenizer is sufficient; check first with
      `grep -oE '[A-Za-z]' file.svg | sort -u` before assuming this holds
      for a new document).
    - Apply the path's own transform matrix to every point, plot with
      matplotlib, set axis limits to the viewBox, invert the y-axis
      (SVG y grows downward), aspect='equal', axis off.
  If the rendered result already contains the full diagram, the bug is
  (a), not (b) — don't re-extract, go fix the display code instead.

9.2 Get a clean full-page vector extraction
    pdftoppm -png -r 150 source.pdf /tmp/page       # raster reference
    pdftocairo -svg source.pdf /tmp/page_full.svg    # full-page vector
  Both worked despite these PDFs being RC4-encrypted with copy:no — the
  encryption only blocks text/content extraction via some tools, not
  rendering/rasterization via poppler's own tools. If pdftocairo ever
  fails outright on a future document, that's the point to flag rather
  than force it.
  pdftocairo's output has NO per-diagram cropping — it's the whole page,
  one flat list of hundreds of <path> elements, each usually sharing one
  transform matrix. This is a DIFFERENT, independent extraction pipeline
  from whatever produced the original ~161 diagrams (see section 5.3) —
  it will NOT reproduce their exact styling by default (see 9.5).

9.3 Locate each diagram's crop box precisely — do NOT guess proportions
  The naive approach (assume N evenly-spaced columns across page width,
  e.g. column width = page_width/N) DRIFTS across a wide grid and will
  clip content by the 4th-7th column even though the first 1-2 columns
  look fine. This happened on the first attempt here — don't repeat it.
  Reliable method: detect each "Reeving N-way" LABEL's precise pixel
  position via ink-density column/row scanning on the RASTER image,
  restricted to a tight y-band (or x-band, for rows) that contains ONLY
  the label glyphs — not the underline beneath them, not pulley circles,
  not caption text below. Getting this band wrong (e.g. accidentally
  scanning the underline instead of the letters) gives confidently wrong
  clustered positions that still look plausible — cross-check against a
  manual crop-and-view of at least one column before trusting it.
  Concretely (numpy on the raster array):
    col_ink = (255 - arr[y0:y1, :]).sum(axis=0)   # darkness per x-column
    threshold = col_ink.max() * 0.1
    # find contiguous runs above threshold, merge runs <150px apart
    # (one run per glyph-cluster; merge gap bridges letter-spacing)
  Do this once for columns (using a y-band that isolates label text) and
  once for rows (using an x-band inside one known-good column, scanning
  the full page height). Verify the detected pitch is CONSISTENT across
  the full range (e.g. 927px every column, not drifting) before trusting
  it — if one detected gap is a clear outlier vs the rest, trust the
  consistent pitch and treat that one detection as noise.
  Crop box per diagram = (label_x - margin, label_y - margin,
  label_x - margin + crop_width, next_row_y - margin), where crop_width
  should comfortably clear the widest diagram content (checked visually)
  without bleeding significantly into the next column.

9.4 Filter paths into per-diagram files (don't duplicate the whole page)
  Convert each pixel crop box to the SVG's own coordinate space using the
  scale factor (PDF page point-size / raster pixel-size — pdfinfo gives
  the former, the PNG's own dimensions give the latter). Then, rather
  than writing the ENTIRE full-page path list into every output file
  (which would bloat each one to ~1.5MB), filter to only the paths whose
  OWN transformed bounding box intersects that diagram's crop rectangle
  (small padding, ~5 units, to avoid edge-case exclusion). This keeps
  output file sizes in the same 50-95KB range as the rest of the fleet's
  diagrams. Write each as a standalone
    <svg xmlns="..." viewBox="x y w h">...filtered paths...</svg>

9.5 Fix the stroke color — pdftocairo output does not match fleet convention
  The ~161 pre-existing diagrams all use stroke="#e8eaed" (light,
  legible against this app's dark background). A fresh pdftocairo
  extraction outputs plain stroke="rgb(0%, 0%, 0%)" (black) instead —
  invisible against the dark background, and easy to miss in review
  since the SVG itself still "looks right" in isolation on a white
  background. Fix both the specific new files (sed replace the stroke
  value) AND rely on the permanent CSS safety net already in index.html
  (`.zoom-inner svg path { stroke: #e8eaed !important; }`) which forces
  the correct color regardless of what any diagram file carries — added
  specifically so this can't silently recur on a future re-extraction.

9.6 Verify before deploying
  Render every new file with the same manual matplotlib technique from
  9.1, tile them into one contact-sheet image, and visually check the
  whole set at once (label, full diagram, caption all present, nothing
  bleeding badly from a neighboring column) before replacing the live
  files. This caught the stroke-color issue and confirmed the crop grid
  was correct across all 15 files in one pass, rather than discovering
  problems one crane at a time after deploy.
  Then: bump CACHE_VERSION in sw.js, copy the new SVGs into
  reeving/svg/, redeploy. No manifest.json changes needed if the
  filenames match what's already referenced there.

10. TAB 5 - COUNTERWEIGHT COMBINATIONS  [CONVERSATION]
--------------------------------------------------------------------------------
Purpose: a new-operator-facing tool for the crane's main superstructure
counterweight (rear ballast stack) - distinct from Tab 1/2's hook-block
auxiliary ballast (aux[] in FLEET_BLOCK_SPEC), which is a different weight
system entirely. Two entry points into the same state: tap plates directly
in a visual stack, or jump straight to a known combination from a dropdown.

10.1 Data source and extraction method
  Person supplied Liebherr doc LTM 1250-5-1-001 (0213656-02), chapter 4.07
  "Counterweight" (c) Liebherr-Werk Ehingen GmbH 2021, as an "unlocked" PDF
  (permissions removed, no longer encrypted - unlike the reeving PDFs in
  section 9, poppler wasn't even needed here for that reason). Still hit an
  obstacle: pdftotext/pdfinfo/poppler-utils were not installed in this
  session's sandbox at all (unlike whatever session wrote section 9 - tool
  availability isn't constant run to run, don't assume section 9's toolchain
  is present). Installed PyMuPDF via pip instead and read the page text
  directly.
  The extracted text was garbled - e.g. "Counterweight" read back as
  "&RXQWHUZHLJKW". This turned out to be a uniform per-character code-point
  shift of -29 applied by the embedded Arial subset font (i.e. real_char =
  encoded_char + 29), NOT a font-rendering bug - decoded correctly for
  every letter, digit, and punctuation mark once identified. Two exceptions
  confirmed by testing: literal ASCII space (0x20) is untouched, not
  shifted; and a handful of already-correct high-value/non-ASCII glyphs
  (e.g. the "+-" copyright-line character at 0xB1, and a bullet-point
  character in a separate LucidaSansUnicode font) are also untouched -
  shift was only applied for character codes <=100 excluding literal space.
  If asked to extract another counterweight-combination PDF later, check
  whether this same shift pattern applies before assuming it does - test
  by decoding one word and confirming it reads correctly, the way this was
  verified here.

10.2 Data shape - it's a subset-sum catalog, not a literal single stack
  Every one of the 21 combinations printed in the source chart was checked
  against the subset-sum of a fixed set of 8 physical components' weights -
  all 21 reconcile exactly, with no remainder. That means the real data
  model is "which of 8 fixed components are present," not a monotonically-
  growing single physical stack - e.g. going from 41t to 43t swaps plate 3
  out for plate 5, it doesn't just add another plate on top. Only these 21
  of the 8 components' 256 possible subsets are OEM-published/approved.
  This directly parallels Tab 1's aux[] philosophy (real OEM combinations
  only, not generic increments) - same reasoning, independently arrived at
  for a different weight system.
  One combination is an exception worth knowing about: the 5t combo is
  plate 6 ALONE - it's the only non-zero combo that does NOT include the
  base receptacle plate (plate 1). Confirmed directly from the source
  chart, not a data-entry error.

10.3 Interaction design - free click + validation, not free click alone
  Considered restricting the click-to-build mode to only ever produce one
  of the 21 known-valid subsets (matching Tab 1's readonly-ballast-dropdown
  philosophy exactly). Person explicitly chose a looser design instead:
  free-click any plate combination, but flag with an explicit warning
  banner - not a silent block, not a silent accept - whenever the resulting
  subset isn't one of the 21 published combos. This mirrors Tab 2's
  precedent (explicit warning banner over silent fallback) rather than
  Tab 1's precedent (hard-block invalid input via readonly field). Don't
  "tighten" this into a hard block in a future pass without asking first -
  it was a deliberate choice, not an oversight.
  The dropdown ("Jump to Known Combination") and the clickable stack share
  the same underlying selection state - selecting from the dropdown updates
  the stack's highlighted plates and vice versa is effectively true too
  (clicking to reconstruct a known combo shows the same "approved" status
  the dropdown entry would have given it).

10.4 Visual design - superseded once, now click-on-the-real-diagram
  Went through two visual designs in the same session before landing.
  v1 (abstract bars): plate weights only, no thickness/footprint/stacking
  sequence in the combination chart (section 10.1's source), so the first
  build used an abstract vertical bar stack - bar height proportional to
  weight, stacking order INFERRED from how combos build up across the
  chart (e.g. plate 1 appears in every non-zero combo except the 5t one,
  suggesting it's the base plate), hook ballast 8 drawn detached since it
  seemed unlikely to be a literal stacked plate.
  The person then supplied a separate OEM exploded-view assembly diagram
  (parts numbered 1-8, matching this tab's component numbering exactly),
  which CONFIRMED the inferred order was right on both counts - plates 1-7
  mount bottom-to-top in exactly that numeric sequence (plate 1, a small
  twin-pin mounting piece, directly on the turntable; plate 7, the
  tallest/boxiest piece, at the top), and component 8 mounts to the LEFT
  and RIGHT sides of the stack rather than on top of it.
  v2 (current - click directly on that diagram): once the order was
  confirmed, the person asked for the click/select interaction to happen
  ON the real diagram itself rather than in an abstract bar list ("easier
  ... to visualize from what's in front of them, not a text box"). This is
  the shipped design. Mechanics:
    - The exploded-view image is embedded directly in the PDF as a RASTER
      (PNG XObject, 1831x1620), not live vector paths - confirmed by
      checking every vector drawing on that PDF page against the image's
      bounding box; zero overlap. So unlike the reeving diagrams (real
      extracted vector SVGs, section 5.3/9), this is a genuine raster
      image, extracted via PyMuPDF's doc.extract_image() and stored as
      counterweight/img/ltm1250-cwt-exploded.png (parallel directory to
      reeving/svg/, same "actual OEM artwork, extracted directly, not
      redrawn" framing, same in-app disclaimer convention).
    - Each component has a hotspots[] array (COUNTERWEIGHT_DATA), rendered
      as an SVG <polygon> overlay (viewBox="0 0 1831 1620", matching the
      diagram's own natural pixel size exactly) positioned over the <img>.
      First pass used generous hand-fit BOUNDING-BOX rectangles (eyeballed
      off a pixel grid overlaid on the raw PNG). Person then asked for the
      highlight to follow each plate's actual silhouette instead ("easier
      ... not a text box" feedback extended to "not a box at all, either").
      Re-derived algorithmically with OpenCV rather than hand-traced:
        1. Crop a generous region around each part (from the same rough
           boxes as the v1 rectangles).
        2. Threshold to a binary ink/paper mask, morphological CLOSE to
           bridge small 1-2px gaps in the linework.
        3. Flood-fill the mask's true exterior from a crop corner; the
           silhouette is everything the flood fill did NOT reach (ink
           itself plus any fully-enclosed interior detail - holes, ridges).
        4. Morphological OPEN (9x9 kernel) to strip thin spikes - this
           specifically removes leader-line-to-callout-number artifacts
           that the first attempt (without this step) picked up as part of
           the plate's own silhouette (e.g. a thin tail running from plate
           6 or plate 5's body up to their number label).
        5. cv2.findContours (RETR_EXTERNAL) on what's left, take the
           largest contour, cv2.approxPolyDP (epsilon = 0.6% of perimeter)
           to reduce point count into a clean polygon.
      Verified by re-drawing every resulting polygon on top of the source
      image and visually confirming a clean fit (no leftover spikes, no
      leakage into neighboring parts) before pasting the point lists into
      COUNTERWEIGHT_DATA. This is closer to a real traced outline than the
      v1 rectangles, but it's still an algorithmic approximation (ink
      thickness inflates the boundary slightly outward; opening can round
      off a genuinely sharp small corner) - not hand-verified point-by-
      point against the CAD source, because there is no CAD source, only
      this raster. If the diagram image is ever replaced (higher-res
      rescan, different crane), this whole derivation needs re-running
      against the new raster - the polygons are fit to this specific PNG's
      pixels, not to anything in the PDF that would carry over automatically.
      Two bugs caught after the first pass shipped, both worth knowing
      about if re-deriving polygons for a future crane's diagram:
        - Plate 1's OPEN kernel (9x9, same as every other part) was large
          enough to sever the thin neck connecting its left mounting post
          to the base plate, silently dropping that post from the
          silhouette entirely. Fixed by using a smaller kernel (3x3) for
          this part specifically - there's no single kernel size that's
          safe for every part, thin real geometry (like this post) can
          look identical to a leader-line artifact to a fixed-size opening.
          Always visually check parts with thin connected sub-features, not
          just the ones near a text label.
        - Plate 1's crop box was also just too small on the right/bottom -
          cut off before the plate's actual right edge and the small
          connector-tab detail near the "11t" label, so that whole corner
          was outside the crop and could never have been traced regardless
          of kernel size. Caught by the person comparing a screenshot
          against the live selection, not by the earlier "re-draw on the
          source image" verification pass - that check confirms the traced
          polygon fits cleanly within its crop, it does NOT confirm the
          crop itself was generous enough to contain the whole part. Pad
          crop boxes more generously than seems necessary, especially near
          image edges or small printed labels/tabs, and specifically check
          each part's true extent against a pixel grid (like section 9.3's
          reeving-diagram approach) rather than eyeballing a bounding box
          once and moving on.
    - Component 8 ("2x Hook Ballast 8") gets TWO hotspots (left box, right
      box in the diagram) that both toggle the SAME single component id -
      it's one logical 20t item in the data model (matching the source
      chart's single "2x Hook Ballast 8: 20.0t" line), just drawn/clickable
      in two places since the physical pair really does mount on both
      sides. Clicking either one selects/deselects both simultaneously.
    - Selected hotspots get a gold outline + translucent fill directly on
      top of the diagram; unselected ones are fully invisible (transparent
      fill/stroke) so the diagram reads clean until something's picked.
      Hover/focus gets a faint stroke for discoverability. Polygons carry
      tabindex/role=button/aria-label and an Enter/Space keydown handler,
      not just a click handler, for basic keyboard reachability - the app
      doesn't do this everywhere (e.g. the CAD tab's canvas has no keyboard
      equivalent), but it was cheap to add here and there's no reason not to.
  The abstract bar-stack (v1's .cwt-stack/.cwt-plate CSS, PX_PER_T sizing)
  and the bounding-box rectangle hotspots (v2) were both removed entirely,
  not kept as fallbacks - don't resurrect either without asking, the
  polygon-on-diagram overlay is the intended interaction now.

10.5 Plate 6 centering notice

  without BOTH plates 3 and 4 also present. Implemented as a second,

10.7 LTM 1110-5.1 added - same session, new patterns needed
  Source: Liebherr doc LTM 1110-5-1-000 (0214357-01), chapter 4.07
  "Counterweight" (pages 12-20/49), (c) Liebherr-Werk Ehingen GmbH 2021 -
  a 14-page excerpt the person supplied directly (not encrypted this time,
  no unlock step needed), confirmed complete (28.2t is genuinely the top
  of the range, not a cut-off). Extracted via the exact same PyMuPDF
  character-shift decode as 10.1 - same -29 offset worked unchanged, worth
  re-verifying on a case-by-case basis anyway (see 10.1's own caution about
  this), but it held here. Also note: poppler/pdftotext was AGAIN not
  installed in this sandbox session (see 10.1 - tool availability isn't
  constant), PyMuPDF was already available from before so no reinstall
  needed this time.

  Unlike 1250, this crane's data didn't fit the existing model unchanged -
  three genuinely new patterns were needed. Don't assume 1250's model is
  "the" model; check for these same three questions before adding a future
  crane:

  a) Non-counting items exist. Two components - "Winch 2*" and "Replacement
     Ballast" - are both 0.8t and occupy the same physical mounting slot
     (confirmed via the diagram - slot 8, above plate 7). Checking every
     combo that lists either one against its own printed total revealed:
     Replacement Ballast's 0.8t always adds to the total; Winch 2*'s 0.8t
     NEVER does (the printed total only reconciles with it excluded, in
     all 8 combos where it appears). This is a real, confirmed OEM
     accounting rule (the winch is a working machine component, not
     ballast, even though it occupies the ballast-adjacent slot and gets
     listed in the same "Composition" breakdown) - NOT a data error, don't
     "fix" it to count like everything else. Modeled as `countsToward:
     false` on the component - cwtComboWeight() skips it when summing, but
     the Composition table still displays it (labeled "not counted in
     total") since the OEM doc does list it as part of the breakdown.
  b) Mutually-exclusive slots exist. Winch 2* and Replacement Ballast can't
     both be present (same physical slot) - at most one of the two is ever
     selected. Modeled via `slotGroup: 'slot8'` on both; clicking the one
     hotspot (only the Winch 2* entry carries actual hotspot points, the
     Replacement Ballast entry's hotspots is deliberately empty) cycles
     none -> Winch 2* -> Replacement Ballast -> none via
     cycleCwtSlotGroup(), rather than a plain per-plate toggle. The visual
     highlight and label reflect whichever member is currently active, not
     always the hotspot-owning component - see the `activeInGroup` lookup
     in renderCwtTab().
  c) Always-paired plates with unresolvable overlapping silhouettes exist.
     Plates 3 and 4 (both 6.0t) appear together in every single one of the
     38 published combos - never one without the other - AND their
     silhouettes overlap with no clean dividing line in the source
     diagram (unlike every other plate pair on both cranes so far, which
     sit with a visible gap). Attempted the same flood-fill contour method
     as everywhere else; it fuses them into one blob because there's
     genuinely no boundary to detect. Rather than guess a line, modeled as
     `linkedId` - plate 4 owns the one clickable region (a generous
     rectangle spanning both, since a precise outline isn't extractable
     here either), and toggling it syncs plate 3 to match via a new check
     in toggleCwtPlate(). The Composition table still lists them as two
     separate 6.0t line items (matching the OEM doc), only the click
     target and highlight are merged.
     Also: 25.4t appears TWICE in the chart with genuinely different
     compositions ({2,3,4,5,+Winch2*} and {2,3,4,6,7,+Replacement
     Ballast}, both on top of 1+3+4) - a real chart quirk, not a
     transcription duplicate, confirmed by both compositions individually
     reconciling to 25.4 by subset-sum. cwtFindMatchingCombo() already
     matches on the full item SET not just total weight, so this doesn't
     cause any ambiguity in validation - only the dropdown needed checking
     (its label lists components, not just weight, so the two entries are
     visually distinct there too).

  Also un-hardcoded three things that were 1250-specific in the first
  build, now crane-generic:
    - The diagram <img>/svg viewBox are no longer fixed to 1250's file and
      1831x1620 - each crane's data carries diagramImage/diagramWidth/
      diagramHeight, applied in renderCwtTab() on every render (cheap,
      idempotent, simpler than trying to only-update-on-crane-change).
    - The Fig./doc-number disclaimer text below the diagram was hardcoded
      HTML; now a `figRef` field per crane, injected via a span.
    - The plate-6-centering notice was a hardcoded check for id 'p6' and
      the literal 1250 warning text. Generalized to loop over any
      component with `centerTrim: true` (currently only 1250's p6) - the
      warning TEXT still hardcodes "plates 3 and 4" since that's what the
      1250 doc's requirement actually says, not a generic placeholder.
  Scope stayed the same as 1250 per the person's explicit choice: no
  fastening/bitt-location detail (section 4 of the 1110 doc, and the
  per-combo pin/bolt/screw "Note" blocks embedded in section 5 itself)
  was surfaced in the tool - out of scope for now, same as 1250.

  Diagram: Fig. 155645 (page 5 of the excerpt), extracted the same way as
  1250's (raster PNG XObject embedded in the PDF, not vector - see 10.4's
  method). This one includes a bonus assembled/composite view alongside
  the exploded stack (kept in the same image, only the left/exploded half
  has hotspots - the assembled half can't be clicked per-part, it's a
  single fused illustration). Hotspot derivation mostly followed 10.4's
  algorithm unchanged, with two new lessons:
    - Kernel size for the morphological OPEN step isn't a fixed constant
      even within one diagram - plate 1's posts needed 3x3 (9x9 severed
      them, same failure mode as 1250's plate 1), everything else here
      used 7x7. Check parts with thin connected sub-features individually,
      don't assume one kernel size works for a whole diagram.
    - Crop boxes were sized generously up front this time (informed by the
      1250 plate-1 lesson), and no post-ship crop-boundary bug turned up
      for this crane as a result - reinforces that the earlier miss was a
      process gap (verify-against-source-image doesn't catch an undersized
      crop, only a bad trace within a correctly-sized crop), not a one-off.

10.8 LTM 1130-5.1 added - different diagram style, per-unit weight trap

  decode as every prior crane, unchanged.

     quirk. The source chart lists "2x auxiliary ballast 8 / Individual
     weight 6.35" for one line. First-pass subset-sum check using 6.35 as

  d) Diagram (Fig.103261) is a different STYLE from 1250/1110 - a side/

10.13 Stray red outline on tapped hotspots - CSS focus-state gap, not a
      data or logic bug
  Person reported a red-tinted highlight on whichever plate was tapped
  most recently on LTM 1650's diagram (screenshot showed one "10t" plate
  glowing red instead of blending into the gold selected state like the
  rest). Root cause: .cwt-hotspot's :hover/:focus-visible rule set
  `outline: none`, but a touch tap on an SVG element with tabindex="0"
  generally produces plain :focus, not :focus-visible, on mobile
  browsers (:focus-visible is mostly reserved for keyboard-driven focus).
  The base .cwt-hotspot rule never reset outline at all, so the browser's
  own default focus ring - independent of this app's palette entirely -
  showed through on tap, layered on top of the correct gold fill/stroke.
  Global CSS already sets -webkit-tap-highlight-color: transparent on
  every element, which handles the WebKit tap-flash overlay, but that's a
  different mechanism from the focus outline - fixing one doesn't fix
  the other.
  Fix: moved `outline: none` onto the base .cwt-hotspot rule so it always
  applies regardless of focus state, keeping the intentional gold stroke
  on :hover/:focus-visible only. This is a general CSS gap, not specific
  to LTM 1650 - it would affect any crane's hotspots on a touch device,
  just hadn't been reported yet. Confirmed fixed via a touch-emulated
  Playwright context (has_touch/is_mobile), not just a regular click -
  a plain .click() doesn't reliably reproduce the same focus state a real
  tap does, worth remembering when testing future touch-only interaction
  bugs on this tab.

10.26 Diagram sizing normalized across all cranes; pinch-to-zoom added
  Two related UI requests. Before this, .cwt-image-wrap used width:100%
  + height:auto on the <img>, so each diagram rendered at ITS OWN native
  aspect ratio - fine while every diagram happened to be roughly
  landscape, but LTM 1110's diagram is portrait (0.80, width < height)
  while every other crane's is landscape (1.13 to 3.57), so 1110 rendered
  more than twice as tall as the others at the same container width,
  dominating the page and requiring much more scrolling to get past it.
  Fixed by giving .cwt-image-wrap a fixed height (min(460px, 60vw), the
  vw term only matters on very narrow viewports) and switching the <img>
  to width:100%/height:100%/object-fit:contain, which letterboxes any
  aspect ratio to fit the same box instead of dictating the box's own
  height. The hotspot SVG needed NO matching logic added - it already
  used preserveAspectRatio="xMidYMid meet" (same letterbox-to-fit
  behavior as object-fit:contain) with position:absolute/inset:0 filling
  the same box as the img, so once both share one fixed-size parent, they
  stay pixel-aligned automatically at any aspect ratio, zoomed or not.
  Verified all 6 cranes now report identical #cwt-image-wrap bounding
  boxes at a given viewport, and that hotspot clicks still land correctly
  on both extreme aspect ratios (1110 portrait, 1300 at 3.57).
  Pinch-to-zoom: added as a self-contained feature (cwtZoomState /
  cwtInitZoom() etc.) applying a CSS transform to a new #cwt-zoom-inner
  element wrapping the img+svg pair, itself a child of the now
  fixed-size, overflow:hidden #cwt-image-wrap - so zooming/panning can
  never grow the page layout, only pan/scale within the fixed box.
  Listeners are bound once (wrap.dataset.zoomBound guard) directly to
  #cwt-image-wrap, which renderCwtTab() never replaces - only the img src
  and the SVG's own children get swapped on re-render, so the zoom
  listeners and current zoom state both survive a crane switch or combo
  selection (zoom state is explicitly reset on crane switch in
  onCwtCraneChange() though, so switching crane doesn't carry over a
  zoom/pan position sized for a differently-shaped diagram).
  Deliberately did NOT set touch-action:none on the wrapper - that would
  block the browser's native single-finger vertical scroll for ANY touch
  starting on the diagram, even when not zoomed in, trapping a user's
  attempt to scroll past the diagram. Used touch-action:pan-y instead
  (blocks native pinch-zoom/horizontal-pan, allows native vertical
  scroll), and only claim a single-finger touch as a pan gesture in JS
  when cwtZoomState.scale > 1 at touchstart - at scale 1, single-finger
  touchmove is never preventDefault'd, so normal page scroll passes
  through untouched. Verified both cases directly: a vertical swipe over
  the diagram at scale 1 scrolls the page (confirmed via window.scrollY
  changing), and the same swipe after zooming in pans the image instead.
  Pinch math: track the two touch points' distance and midpoint at
  gesture start, scale relative to that start distance, and solve
  translate each frame so the content point that was under the midpoint
  at gesture start stays there as scale changes (standard "anchor the
  pinch center" approach) - without this the image would zoom from its
  top-left corner instead of from wherever the fingers actually are.
  Clamped so panned/zoomed content can never show empty space past its
  own edge (cwtClampZoomState). Double-tap and double-click both reset to
  1x - the only way back without a dedicated UI button - gated on the
  gesture never having moved (hadGesture flag) so releasing a real pinch
  or pan doesn't also fire a false reset.
  Verified end-to-end via Chromium's CDP Input.dispatchTouchEvent (not
  just Playwright's synthetic .tap(), which can't simulate true
  multi-touch): two-finger pinch reaches scale 4 and clamps there,
  single-finger drag after zooming in pans and updates translate to match
  the finger's exact delta, and double-tap correctly resets state to
  {scale:1, tx:0, ty:0}.

10.28 Real bug: counterweight diagrams could never actually update on a
      returning user's device, regardless of how many times
      CACHE_VERSION was bumped
  Person reported still seeing the old black-background LTM 1650 diagram
  after refreshing, despite 10.27's fix being live on main with a fresh
  CACHE_VERSION. Root cause: counterweight diagram images were never in
  sw.js's APP_SHELL list (only index.html/manifest/icons were) - the
  service worker's fetch handler cache-first-then-network's everything
  NOT in APP_SHELL into CONTENT_CACHE, a permanently-unversioned cache
  that the activate handler explicitly never clears (intentional, so a
  crew doesn't lose offline access to reeving diagrams they've already
  viewed across app updates). The first time anyone's browser fetched a
  counterweight diagram, it landed in CONTENT_CACHE and stayed there
  forever - every subsequent CACHE_VERSION bump only ever touched
  APP_SHELL_CACHE, which these images were never part of. This means
  EVERY counterweight diagram fix shipped this session (10.24's LTM 1160
  replacement, 10.23's LTM 1300 addition, 10.27's LTM 1650 invert) was
  invisible to anyone who'd viewed that crane's tab before the fix
  shipped, no matter how many version bumps followed.
  Fix, two parts:
  a) Added all 6 counterweight diagram paths to APP_SHELL, so they're
     precached and refreshed on every CACHE_VERSION bump exactly like
     index.html.
  b) That alone isn't sufficient - a stale copy could already be sitting
     in CONTENT_CACHE from before this fix, and caches.match() (used by
     the fetch handler for anything not explicitly checked against a
     named cache first) doesn't guarantee it prefers the newer entry in
     APP_SHELL_CACHE over an older one in CONTENT_CACHE; iteration order
     across caches isn't something to rely on. Fixed by (1) making the
     fetch handler check APP_SHELL_CACHE explicitly FIRST and return
     immediately on a hit, before ever consulting CONTENT_CACHE, and (2)
     having the activate handler purge any CONTENT_CACHE entry whose URL
     matches something now in APP_SHELL, cleaning up the orphaned
     duplicate rather than leaving it to linger unused.
  Verified with a real service-worker lifecycle test, not just a code
  read-through - Playwright against a local server, swapping the served
  sw.js and image mid-test to simulate "old file cached on a device" then
  "fix deployed to origin, browser checks for SW update":
    1. Serve the OLD sw.js (pre-fix, matching what was actually live) and
       the OLD black image. Load the app, browse to LTM 1650, confirm the
       image is black and lands in CONTENT_CACHE (reproducing the bug).
    2. Swap the served files to the NEW sw.js and the NEW white image
       (simulating a fresh deploy to origin) without touching the
       already-loaded page.
    3. Call registration.update() and wait for the controllerchange
       event specifically (not just polling reg.active, which can
       resolve fractionally before THIS client's controller actually
       flips over and produced a false negative on an earlier, less
       careful pass at this same test).
    4. Reload and re-check the same <img> element used by the real
       Counterweight tab: black -> white, confirmed pixel-for-pixel.
  Also confirmed CONTENT_CACHE's stale entry for the same URL was gone
  after the new SW activated, not just shadowed.
  This class of bug - "shipped a fix, bumped the version, it's still not
  visible" - won't recur for future counterweight diagram changes now
  that they're in APP_SHELL, but is worth remembering as a category: any
  asset that CAN change over the app's development lifetime needs to be
  in the versioned precache, not left to fall into the permanent content
  cache by default just because it's an image fetched on demand.

10.43 LTM 1110's Rear table was badly truncated - fixed with a fuller PDF,
      and hit a genuinely new extraction bug along the way
  Person: "i missed a few pages from the list so look over it again more
  on the to the rear side of things," with a re-supplied version of the
  same document (same doc code 0213844-00/ver_2197110102) - this one 5
  pages instead of the original 2. Page 0 is Front, unchanged from what
  was already shipped. Pages 1-4 are ALL "Boom direction to the rear"
  (same vtab_..._02001_00_000 code repeated across all four) - one long
  table continuing across page breaks, not four separate charts. The
  original 2-page PDF only had page 1 of that continuation, so 10.41's
  Rear data stopped at 24.4t - the real table goes all the way to 0.0t.
  This version of the document also turned out to have the -29
  character-shift cipher active (10.41's original 2-page PDF did not -
  confirms per-document/per-export encoding is not something to assume
  either way, per the earlier note to build a training reference for
  this).
  Hit a new, nastier variant of the digit-decoding bug first found on
  LTR 1220 (10.39): calling .strip() on a span's RAW, still-encoded text
  - either to trim it or just to test truthiness before deciding whether
  to keep it - silently corrupts or drops content, because several of
  the cipher's control-character byte values for digits (found here:
  raw \x1c, representing digit '9') fall inside Python's Unicode
  whitespace definition. Two distinct symptoms from the same root cause:
  calling .strip() and keeping the result truncated "10.9" down to
  "10." (lost the trailing digit); calling raw.strip() only as an
  emptiness check before appending the (unstripped) text dropped entire
  rows outright, whenever a span's encoded bytes happened to ALL fall in
  that whitespace-like range. Fix: never call .strip() on cipher text
  before decoding - decode first with the +29 shift, THEN strip/test the
  decoded (now normal-ASCII) result if needed. Also had to special-case
  the degree sign here: its raw byte (0x83) doesn't survive the
  no-wraparound +29 shift into the correct Unicode code point for '°'
  (U+00B0/176) the way ASCII letters/digits do, so it's mapped
  explicitly rather than trusting the arithmetic.
  Re-extracted all 5 pages with the fixed decoder: page 0 (Front) came
  back byte-identical to what's already shipped, confirming no other
  damage; pages 1-4 (Rear) combined to 78 rows across 39 distinct
  counterweight values (previously only 12 were shown), every one with
  exactly 2 boom-angle-range options, continuity checked at every page
  break (e.g. 24.4t's second option starts page 2 right after its first
  option ends page 1, no gap or duplicate). Replaced the Rear rows array
  wholesale rather than appending, since the old 12-weight set was a
  strict prefix of the new 39. Verified in-browser: Rear now lists 39
  weights, 0.0t shows both options correctly, Front (14 weights) and
  LTM 1300 unaffected.
